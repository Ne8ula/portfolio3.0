# Phase 3 DPR evidence

This directory holds the environment-separated captures required by
`docs/phase-3-design.md` §5 and AC-23. Captures are measurements, not visual
scorecard baselines. Phase 4's renderer-specific scorecards remain out of
scope.

Required completed evidence before Phase 3 can close:

1. one software capture generated by Codex with its unmasked renderer string;
2. one hardware capture generated on the owner's real high-DPR laptop with
   its unmasked renderer string;
3. the owner's certification of that hardware environment and the one-time
   `about:gpucrash` recovery run in a completed copy of
   `OWNER-CHECKPOINT.template.md`.

Software and hardware results are never compared to each other. SwiftShader
numbers exercise the harness only and can never justify changing `DPR_CAP`.
The hardware capture is not certified merely because the script completes;
the owner checkpoint is a separate human record.

## Capture commands

Build once and retain the build output:

```sh
NEXT_PUBLIC_SITE_URL=https://preview.example.com npx next build --webpack 2>&1 | tee /tmp/phase-3-next-build.log
npm run start
```

In another terminal, a software capture uses bundled Chromium with
SwiftShader forced:

```sh
npx tsx scripts/perf/dpr-baseline.ts \
  --capture-kind software \
  --environment-id software-swiftshader-YYYY-MM-DD \
  --build-log /tmp/phase-3-next-build.log
```

The owner hardware capture should use a unique environment id, a real Chrome
channel, an explicit power state, and a headed browser:

```sh
npx tsx scripts/perf/dpr-baseline.ts \
  --capture-kind hardware \
  --environment-id owner-hardware-YYYY-MM-DD \
  --browser-channel chrome \
  --headed \
  --power-state mains \
  --hardware-model "OWNER-SUPPLIED MODEL" \
  --build-log /tmp/phase-3-next-build.log
```

Each command writes one JSON raw record and one Markdown summary. The harness
uses the approved production-build matrix without adjustable timing: four CSS
viewports × cockpit/crate/deck × DPR 1/2, with a 5 s warm-up and 15 s rAF
sample per cell. It records frame-time and FPS distributions, renderer
counts, memory counts, JS heap when Chromium exposes it, drawing-buffer
dimensions, observed DPR, bundle/build metadata, and mandatory
`WEBGL_debug_renderer_info` unmasked vendor/renderer strings.

The harness rejects a software run that does not resolve to a known software
renderer and rejects a hardware run that resolves to SwiftShader, llvmpipe, or
another named software rasterizer. It also rejects development servers by
checking that `__COCKPIT_TEST_HOOKS__` is absent.

The local `next start` preview currently logs one 404 per browser page for
`/_vercel/insights/script.js`. Capture diagnostics retain that message; a
network probe must identify it before review so it is not mistaken for a
WebGL or application-resource failure.

## Decision boundary

`DPR_CAP` remains `2` while owner evidence is pending. After Kimi independently
passes this Step 7 diff, stop at the owner checkpoint. Only the
owner-certified hardware result at `1512×982`, comparing DPR 1 with DPR 2 in
both crate-focused and deck-focused views, can support the §5.4 decision:

- retain `2` when DPR 2 holds median frame time ≤ 16.7 ms and p95 ≤ 33.3 ms
  in both views;
- prepare an owner-approved amendment only if either view fails at DPR 2
  while the same view passes at DPR 1.

Ultrawide or large-smoke breaches alone do not justify a cap change. No
decision or owner certification is recorded by the capture script.
